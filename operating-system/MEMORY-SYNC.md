# Shared brain: memory, improvement and synchronization
Version 1.1.0 | Private source of truth: https://github.com/trevorcrane/epic-ai-os

## Durable record
Git version history holds portable instructions, skills, routing, approved lessons and scoped messaging maps. A chat is evidence, not the only memory store. Long-term retention requires maintaining access and backups; no file guarantees memory forever or automatic adoption by every model.

Separate four layers: shared operating rules; generic skills; brand-specific messaging/voice/facts; job evidence and outcomes. A correction to Leigh’s launch does not rewrite Robyn’s voice. Credentials and sensitive client records do not belong in generic skill exports.

## Improvement loop
At the end of relevant work, capture corrections and results in a lesson record: ID, date, source, owner statement vs agent inference, brand/global scope, before/after, accepted and rejected ideas, evidence, affected files and proposed status. Explicit owner preferences can be recorded immediately. Hypotheses remain proposed until validated. Performance lessons require actual metric, denominator, date range and attribution limits.

Update the smallest appropriate file: role behavior in Cat’s brief, reusable method in her skill, voice/positioning in the relevant brand messaging map, tool usage in its procedure, deployment facts in the adoption register. Keep historical source and supersession links. Do not append contradictory rules indefinitely.

Propose changes through a Git branch and reviewable commit/PR. Read the current remote version before writing; preserve concurrent work, never force-push over other agents. A pending review branch is stored but not the default canonical release. Pin adapters to an accepted commit, advance them after review, and retain a rollback revision. Existing merge authority applies; do not invent merge approval from a memory-capture request.

## Recurring review
Default maintenance cadence for this request: nightly at 9 PM America/New_York, adjustable by Trevor. Review only newly available task notes and authorized lesson submissions since the stored cursor. Deduplicate by source + lesson ID. Capture and refine proposed changes; do not manufacture lessons on empty runs. Keep quiet when there is no actionable change. Notify only meaningful changes, failures or owner decisions. Never send, publish campaign copy or claim remote installations because a timer fired.

The scheduled Codex heartbeat is a convenience, not the cross-platform source of truth. Other harnesses may run this same maintenance procedure using their supported scheduler. Avoid multiple writers to the same file: one steward per change set, separate branches for concurrent changes. Without access, save a pending lesson for the steward instead of pretending to sync.

## Adoption receipt
For each runtime record: identity, harness, repository URL, exact commit, loaded paths, load time, test result and gaps. Test: ask the runtime to explain the waitlist-vs-purchase distinction, identify Ojoy as optional, and locate the critique prompt. File receipt alone does not prove behavioral adoption. Repeat after restart or version change. Never claim access just because the roster lists a tool.

## Portability and backups
Use Markdown plus a small manifest. Core instructions stay the same; adapters map them to each host’s supported instruction/skill surfaces. Distribute a sanitized export for wife/client installations. Maintain repository access and an encrypted backup under the owner’s existing backup policy; do not create new public mirrors. Remote deployment status belongs in adapters/ADOPTION.md.
